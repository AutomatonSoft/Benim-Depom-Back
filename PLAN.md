# План реализации backend-проекта

> Это рабочий план первой версии, а не финальное ТЗ. Новые требования, поля товара,
> интеграции и правила модерации будут уточняться по ходу разработки и добавляться
> отдельными небольшими задачами.

## 1. Цель первой версии

Backend обслуживает два клиента:

- мобильное приложение для продавцов;
- сайт для менеджеров и администраторов.

Продавец регистрируется, входит по логину и паролю, создаёт товар с фотографиями и
отправляет его на проверку. Менеджер видит товар на сайте, одобряет либо отклоняет его,
а пользователь получает уведомление. После одобрения товар в дальнейшем можно будет
отправить на маркетплейс через предоставленный внешний endpoint.

На старте чат не делаем. Вместо него будут push-уведомления и экран уведомлений внутри
мобильного приложения.

## 2. Выбранный стек

- **Python + Django + Django REST Framework** — API, авторизация, права доступа,
  миграции и работа с данными.
- **PostgreSQL** — основная база данных.
- **Redis** — очередь задач и кэш.
- **Celery + Celery Beat** — фоновые и периодические задачи.
- **Firebase Cloud Messaging (FCM)** — push-уведомления в мобильное приложение.
- **Firebase Phone Auth** — SMS-подтверждение номера как второй фактор; точный сценарий
  подключения уточняется с мобильным разработчиком.
- **S3-совместимое объектное хранилище** — фотографии товаров. Локально подойдёт MinIO,
  в production — выбранное облачное хранилище.
- **Docker Compose** — локальный запуск сервисов.
- **Pytest, Ruff, mypy (по мере необходимости)** — тесты и качество кода.
- **Sentry** — отслеживание ошибок в production.
- **OpenAPI / Swagger** — документация контракта API для mobile и web frontend.

## 3. Принцип архитектуры

Начинаем с **модульного монолита**, а не микросервисов. Для ожидаемой нагрузки
(до 500–1000 пользователей с запасом) это проще, надёжнее и быстрее в поддержке.

Примерная структура:

```text
apps/
  accounts/         # пользователи, роли, авторизация, 2FA
  products/         # товары, фото, характеристики, статусы
  catalog/          # типы, материалы, категории, цвета
  moderation/       # решения менеджеров и история статусов
  notifications/    # FCM, уведомления в приложении, токены устройств
  integrations/     # AI-обработка фото и будущие маркетплейсы
  audit/            # история важных действий
  common/           # общие исключения, permissions, базовые классы
```

Правила реализации:

- API-представления не содержат бизнес-логику: они вызывают сервисы приложения.
- Доступ проверяется backend-ом через роли и permissions, а не только frontend-ом.
- Внешние вызовы (AI, FCM, маркетплейсы) выполняются в фоновом режиме с таймаутами,
  логами и ограниченными повторами.
- Важные изменения фиксируются в истории: кто, что и когда поменял.
- Настройки и секреты хранятся в переменных окружения, не в репозитории.

## 4. Роли

- **seller** — пользователь мобильного приложения; видит и изменяет только свои товары.
- **manager** — работает с товарами всех продавцов, принимает решение по модерации.
- **admin** — управляет менеджерами и системными справочниками.

## 5. Базовые сущности первой версии

- `User` — имя, email/логин, пароль в хэшированном виде, телефон, язык, роль, статус.
- `DeviceToken` — FCM-токен конкретного устройства пользователя.
- `Product` — владелец, тип/категория, статус, количество, служебные даты.
- `ProductImage` — ссылка на оригинальное и, позже, обработанное изображение, порядок,
  статус обработки.
- `ProductVariant` — цвет, материал, ширина, высота, длина и количество.
- `Category`, `ProductType`, `Material`, `Color` — справочники. Способ управления ими
  будет уточнён: через менеджерский сайт, мобильное приложение или оба варианта.
- `ModerationDecision` — решение менеджера, комментарий/причина отказа, дата.
- `Notification` — уведомление внутри приложения, тип, текст, статус прочтения.
- `AuditLog` — запись критичных действий для расследования ошибок.

Дополнительные поля товара (название, цена, бренд, описание, вес и т. д.) пока не
фиксируем — добавим отдельной миграцией после согласования.

## 6. Статусы товара

Минимальная модель состояний:

```text
draft → submitted → under_review → approved
                                 ↘ rejected
```

- `draft` — продавец ещё редактирует товар;
- `submitted` / `under_review` — товар ожидает или проходит проверку;
- `approved` — менеджер одобрил товар;
- `rejected` — менеджер отклонил товар с причиной.

Позже без ломки модели добавим `publishing`, `published`, `needs_changes`, `archived`
и статусы синхронизации с маркетплейсами.

## 7. Этапы разработки

### Этап 1. Основа проекта

- Создать Django-проект и модульную структуру.
- Поднять Docker Compose: backend, PostgreSQL, Redis, worker Celery, Celery Beat.
- Настроить `.env.example`, конфигурации development/production, логи и healthcheck.
- Подключить Swagger/OpenAPI.
- Настроить форматирование, линтеры, тесты и базовый CI.

**Результат:** проект стабильно запускается локально одной командой, есть проверка
здоровья API и документация.

### Этап 2. Пользователи, пароль и доступы

- Регистрация по логину/email и паролю.
- Безопасное хэширование пароля, access/refresh JWT-токены, logout и обновление токена.
- Роли `seller`, `manager`, `admin` и server-side permissions.
- Профиль пользователя: имя, телефон, выбранный язык (`ru`, `tr`, `de`, `en`).
- Подготовить второй фактор через номер телефона и SMS/Firebase.
- Ограничить частые попытки входа и добавить журнал важных действий.

**Результат:** mobile и web frontend могут безопасно авторизовывать пользователей с
разными ролями.

### Этап 3. Справочники и товары

- Реализовать модели товара, фото и вариантов с размерами.
- CRUD товаров для продавца: создать, посмотреть список, открыть, изменить, удалить
  (предпочтительно мягко — через архивирование).
- Фильтрация и пагинация списков.
- Справочники типов, категорий, материалов и цветов.
- Определить после уточнения, кто может создавать элементы справочников.
- Добавить индексы для частых запросов: владелец, статус, дата создания, категория.

**Результат:** продавец полностью ведёт собственные товары из мобильного приложения.

### Этап 4. Загрузка и обработка фото

- Подключить объектное хранилище.
- Выдавать временные ссылки для безопасной загрузки изображений напрямую в хранилище.
- Проверять размер, формат и количество фотографий.
- Подготовить клиент к вашему API обработки фото с белым фоном.
- Запускать обработку в Celery после загрузки, сохранять статус и результат.

**Результат:** фото надёжно хранятся, а тяжёлая обработка не блокирует API.

### Этап 5. Модерация на сайте

- Список всех товаров для менеджера.
- Фильтры по статусу, продавцу, дате, типу/категории и другим доступным параметрам.
- Детальная карточка товара с фото и историей изменений.
- Approve/reject; для reject — обязательная причина.
- Запись решений в историю и уведомление продавцу.

**Результат:** менеджеры проверяют товары через сайт, а пользователи видят итог в
приложении.

### Этап 6. Уведомления

- Регистрация FCM-токена устройств после входа в приложение.
- Отправка push при одобрении, отклонении и изменении статуса товара.
- Сохранение уведомлений в базе для экрана «Уведомления» в приложении.
- API списка уведомлений и отметки о прочтении.
- Периодическая задача Celery Beat: через настраиваемый срок (14 или 28 дней) напомнить
  пользователю уточнить, актуален ли товар.

**Результат:** пользователь не пропускает действия менеджера и важные напоминания.

### Этап 7. Интеграции после получения endpoint’ов

- Получить API-документацию AI-сервиса и endpoint’ов маркетплейса.
- Реализовать отдельные клиенты/адаптеры интеграций.
- Передавать товар на публикацию только после approval.
- Хранить внешний ID, статус синхронизации и технические ошибки.
- Добавить безопасные повторы запросов, таймауты и защиту от двойной публикации.

**Результат:** можно подключать маркетплейсы без смешивания их логики с товарами и
модерацией.

### Этап 8. Проверка перед production

- Unit-тесты сервисов, permissions и переходов статусов.
- API/integration-тесты основных сценариев.
- Проверка фоновых задач и обработки ошибок внешних сервисов.
- Настройка резервного копирования PostgreSQL.
- Подключение Sentry, production-логов и мониторинга.
- Настройка CORS, HTTPS, лимитов запросов и безопасного хранения секретов.
- Подготовка понятного README по запуску, миграциям и деплою.

## 8. Минимальные группы API

```text
/auth/…                    # регистрация, вход, refresh, 2FA
/me/…                      # профиль, язык, устройства
/products/…                # товары продавца, фото, отправка на модерацию
/catalog/…                 # типы, категории, цвета, материалы
/manager/products/…        # просмотр, фильтрация, approve/reject
/notifications/…           # список и прочтение уведомлений
```

Точные названия, поля запросов и ответов будут зафиксированы в OpenAPI после получения
документации от mobile/frontend и внешних endpoint’ов.

## 9. Что сознательно откладываем

- чат менеджер ↔ пользователь;
- точные дополнительные поля товара;
- финальные правила создания справочников;
- конкретные маркетплейсы и их API;
- точный формат AI API для белого фона;
- окончательный сценарий SMS как второго фактора;
- real-time обновления через WebSocket.

Это не блокирует старт: архитектура позволит добавить каждый пункт отдельным модулем или
небольшим расширением.

## 10. Критерий готовности первой версии

1. Пользователь регистрируется и входит по паролю.
2. Пользователь создаёт и редактирует свой товар с фото и базовыми характеристиками.
3. Пользователь отправляет товар на модерацию.
4. Менеджер видит все товары, фильтрует их и одобряет/отклоняет с причиной.
5. Пользователь получает push и видит уведомление внутри приложения.
6. Все ключевые действия защищены ролями, покрыты тестами и не выполняют тяжёлую работу
   непосредственно в HTTP-запросе.
