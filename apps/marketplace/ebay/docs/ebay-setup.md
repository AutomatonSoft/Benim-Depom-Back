# Авторизация eBay и уведомления об удалении аккаунта

На этом этапе реализовано подключение продавцов JV, XL и Depotum к eBay.
Публикация товаров и распределение EAN будут добавлены отдельно.
Ни один из этих эндпоинтов не удаляет аккаунт на eBay.

## Настройки сервера

Укажите следующие значения в окружении сервера. Не коммитьте секреты.

| Настройка | Stage | Прод |
| --- | --- | --- |
| `EBAY_ENVIRONMENT` | `sandbox` | `production` |
| `EBAY_PUBLIC_BASE_URL` | `https://stage.benimdepom.info` | `https://benimdepom.info` |
| App ID (OAuth Client ID) | `EBAY_SANDBOX_APP_ID` | `EBAY_PROD_APP_ID` |
| Cert ID (OAuth Client Secret) | `EBAY_SANDBOX_CERT_ID` | `EBAY_PROD_CERT_ID` |
| `EBAY_RUNAME` | OAuth RuName для Sandbox | OAuth RuName для Production |
| `EBAY_TOKEN_ENCRYPTION_KEY` | Отдельный ключ Fernet | Другой отдельный ключ Fernet |
| `EBAY_NOTIFICATION_VERIFICATION_TOKEN` | Случайный токен подтверждения | Другой случайный токен подтверждения |

`EBAY_CLIENT_ID` и `EBAY_CLIENT_SECRET` — внутренние настройки Django: они берутся
из переменных выбранного окружения. Добавлять их в `.env` не нужно.
Существующие `EBAY_SANDBOX_DEV_ID` и `EBAY_PROD_DEV_ID` можно оставить в `.env`;
текущая авторизация через REST OAuth не использует Dev ID.
Ключи приложения общие для JV, XL и Depotum. Каждый продавец проходит авторизацию
отдельно и получает собственные токены, которые сохраняются в системе.

Создайте ключ шифрования локально:

```sh
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Создайте токен подтверждения адреса уведомлений локально:

```sh
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Храните ключ шифрования в безопасном месте и сохраняйте его резервную копию.
Замена ключа сделает уже сохранённые токены нечитаемыми.
Токен подтверждения уведомлений — отдельное значение, а не Client Secret или токен доступа eBay.
Установите зависимости, примените миграции и выкатите бэкенд перед настройкой адресов в eBay.

## Настройка кабинета eBay Developer

Для Production откройте **Alerts & Notifications → Marketplace Account Deletion** и заполните:

- **Notification endpoint:** `https://benimdepom.info/api/v1/ebay/account-deletion/`
- **Verification token:** точное значение `EBAY_NOTIFICATION_VERIFICATION_TOKEN` на проде.
- **Alert email:** рабочий адрес компании, на котором отслеживаются уведомления.

При сохранении eBay автоматически отправляет проверочный GET-запрос с `challenge_code`.
К этому моменту эндпоинт должен быть доступен публично.
GET возвращает SHA-256 ответ на проверку и не меняет данные.
POST проверяет `X-EBAY-SIGNATURE` публичным ключом eBay, затем удаляет соответствующее
локальное подключение eBay и незавершённые попытки авторизации.
Пользователи BENIM, товары и данные остальных маркетплейсов не удаляются.
Содержимое уведомлений и пользовательские токены не сохраняются в логах или таблицах входящих уведомлений.
Повторное подлинное уведомление безопасно: если подключение уже отсутствует, удалять нечего.
После добавления хранения листингов и заказов eBay обработчик потребуется дополнить
удалением связанных с аккаунтом данных.

В разделе **User Tokens** создайте RuName с поддержкой OAuth.
В поля **Auth Accepted URL** и **Auth Declined URL** укажите:

- Sandbox: `https://stage.benimdepom.info/api/v1/ebay/oauth/callback/`
- Production: `https://benimdepom.info/api/v1/ebay/oauth/callback/`

Также укажите адрес опубликованной политики конфиденциальности BENIM.
Скопируйте идентификатор RuName в `EBAY_RUNAME`.
Именно этот идентификатор отправляется в параметре `redirect_uri`, а не адрес callback.

## Подключение продавцов

От имени авторизованного менеджера BENIM отправьте запрос:

```http
POST /api/v1/ebay/oauth/start/
Content-Type: application/json
Authorization: Bearer BENIM_MANAGER_ACCESS_TOKEN

{"account":"jv"}
```

Вместо `BENIM_MANAGER_ACCESS_TOKEN` подставьте токен доступа менеджера BENIM.
Откройте полученный `authorization_url` в браузере и разрешите доступ от соответствующего продавца eBay.
На stage используйте тестового продавца Sandbox, на проде — реального продавца.
Повторите авторизацию для `{"account":"xl"}` и `{"account":"depotum"}` с соответствующими продавцами.

Для определения неизменяемого ID продавца запрашивается разрешение
`https://api.ebay.com/oauth/api_scope/commerce.identity.readonly`.
Identity API использует домен `apiz.ebay.com` (Sandbox: `apiz.sandbox.ebay.com`);
запросы OAuth-токенов используют обычный домен `api`.
После изменения набора разрешений начните авторизацию заново через `/oauth/start/`:
обновление старой страницы callback не выдаст токен с новыми разрешениями.

Callback возвращает подтверждение подключения без раскрытия токенов.
Внутренняя функция `get_access_token` обновляет истекающие токены при обращении к ней.
`GET /api/v1/ebay/connections/` возвращает менеджеру список подключений и сроки действия токенов,
но не сами токены.
Одного пользователя eBay нельзя привязать к нескольким аккаунтам в одном окружении.

## Проверка готовности аккаунта

После подключения JV вызовите от имени менеджера:

```http
GET /api/v1/ebay/readiness/?account=jv
Authorization: Bearer BENIM_MANAGER_ACCESS_TOKEN
```

В Swagger эндпоинт находится в разделе **eBay**. Передайте `account=jv`.
Проверка использует текущее окружение сервера и площадку `EBAY_DE`.
Токен продавца берётся из сохранённого подключения; передавать его вручную не нужно.
Если токен истекает, бэкенд обновляет его через refresh token и сохраняет новое значение.

Эндпоинт читает регистрацию и месячные лимиты, участие в Business Policies,
политики доставки, оплаты и возврата для Германии, а также все страницы складов.
Товары и настройки продавца на eBay не изменяются.

| Поле ответа | Значение |
| --- | --- |
| `checks_complete` | Все запросы к eBay завершились успешно |
| `ready_for_listing_setup` | Получены базовые настройки для подготовки листинга |
| `seller_registration_completed` | Завершена ли регистрация продавца |
| `selling_limit` | Лимиты количества и суммы из eBay; `null`, если данные не получены или лимит не указан |
| `business_policies_enabled` | Подключена ли программа `SELLING_POLICY_MANAGEMENT` |
| `policies` | Идентификаторы и названия политик; `applicable_to_furniture` показывает применимость к обычным товарам на `EBAY_DE` |
| `inventory_locations` | Ключи складов, состояние и краткий адрес; `usable` учитывает доступность склада и наличие адреса |
| `missing_requirements` | Полученные от eBay настройки, которых не хватает |
| `errors` | Ошибки отдельных запросов: HTTP-код, а также `errorId` и `message`, если eBay их вернул |

Успешный HTTP-ответ `200` может содержать неполный отчёт: проверяйте `checks_complete` и `errors`.
Пустой список означает отсутствие ресурсов, а `null` при ошибке означает, что данные не удалось получить.
При частичной ошибке бэкенд сохраняет в ответе остальные успешно проверенные разделы.
Диагностика включает не более трёх ошибок eBay и до 500 символов каждого сообщения.
Полное тело ответа, параметры ошибки и заголовки авторизации не возвращаются;
совпадения с токеном доступа в сообщениях скрываются.
Склады читаются с пагинацией; адрес следующей страницы из ответа eBay не используется напрямую.
На обход отводится 45 секунд до запуска следующего запроса; уже начатый запрос может завершиться позже
в пределах своего таймаута. Автоматические повторы в этой ручной проверке отключены.

`ready_for_listing_setup=true` не гарантирует публикацию конкретного товара и не проверяет
достаточность лимита для его цены и количества. Категория, атрибуты, изображения, условия
доставки и остальные требования предложения проверяются на следующих этапах.
Значения Sandbox не определяют ограничения реального продавца в Production.

## Категории и характеристики EBAY_DE

Справочники доступны только менеджерам и администраторам, в разделе **eBay** Swagger.
В Sandbox используются локальные JSON из `data/ebay/sandbox/`, ключи eBay не нужны.
В Production используется токен приложения (`client_credentials`) по ключам Production.
OAuth-подключение продавца, завершённая регистрация, политики и склад
для чтения справочников не нужны. Дополнительные env-переменные не требуются.

### Навигация по категориям

```http
GET /api/v1/ebay/catalog/categories/
```

Без параметров в Sandbox возвращает категорию мебели `Möbel` (`3197`),
в Production — верхний уровень дерева Германии. В каждом элементе
`categories` есть `id`, `name` и `is_leaf`. Для просмотра следующего уровня:

```http
GET /api/v1/ebay/catalog/categories/?parent_id=<id из предыдущего ответа>
```

`parent` описывает выбранную категорию; у конечной категории список детей пустой.
В ответе также есть `environment`, `marketplace_id`, `category_tree_id`
и `category_tree_version`. Неизвестная категория возвращает `404`, неверный
формат ID — `400`. Полное дерево наружу не передаётся.

### Характеристики конечной категории

```http
GET /api/v1/ebay/catalog/categories/<category_id>/aspects/
```

Принимается ID с `is_leaf=true`. Родительская категория возвращает `400`.
Ответ содержит:

- `category` — выбранную категорию;
- `aspects` — исходные характеристики eBay, включая `aspectConstraint`,
  `aspectValues`, зависимости и прочие доступные поля;
- `required_aspects` — названия, у которых `aspectConstraint.aspectRequired=true`;
- окружение, площадку, ID и версию дерева.

Рекомендуемую характеристику нельзя считать обязательной только из-за
`aspectUsage=RECOMMENDED`: смотреть нужно на `aspectRequired`.
Получение схемы не сохраняет категорию или значения в товаре и не проверяет
заполненный товар. Это отдельный этап интеграции.

### Кеш и Sandbox

В Sandbox `categories.json` содержит ветку мебели; `aspects/<category_id>.json` —
характеристики её конечных категорий. Внешние запросы и получение токена не выполняются.
Категории вне этой ветки возвращают `404`. Отсутствующий или повреждённый JSON
возвращает ошибку; отсутствующие файлы и несовпадение версии характеристик с деревом — `503`.
Автоматического перехода на API нет. Файлы включаются в Docker-образ из `data/ebay/`.
Локальные данные кешируются на 24 часа по пути, размеру и времени изменения файла:
обновлённый файл читается без ожидания истечения кеша. Сам каталог автоматически
не скачивается; снимок нужно обновлять отдельно.

В Production поведение сохранено: дерево и характеристики кешируются на 24 часа; ключ характеристик включает
версию дерева. Токен приложения переиспользуется до срока обновления.
Кеши разделены по окружению и Client ID. Ошибки и повреждённые ответы
не сохраняются как пустые успешные справочники. На первом обращении загружается
полное дерево для серверной навигации, поэтому оно медленнее последующих.

Автоматические повторы GET для этих ручных запросов отключены;
таймаут внешнего GET — 5 секунд на соединение и 10 секунд на чтение.
Время первого обращения также включает получение токена и ID дерева.

`getCategorySuggestions` не используется: официальная документация предупреждает
о шаблонных названиях в Sandbox. Нет автоматического переключения на Production.
Здесь реализована навигация по дереву, а не поиск по ключевым словам.

Источники: [Taxonomy API](https://developer.ebay.com/api-docs/commerce/taxonomy/static/overview.html),
[getCategorySuggestions и ограничения Sandbox](https://developer.ebay.com/api-docs/master/commerce/taxonomy/openapi/3/commerce_taxonomy_v1_oas3.json).

## Локальный черновик объявления JV

Маршрут доступен только менеджеру или администратору:

```http
GET   /api/v1/ebay/drafts/jv/<product_id>/
PUT   /api/v1/ebay/drafts/jv/<product_id>/
PATCH /api/v1/ebay/drafts/jv/<product_id>/
```

- GET возвращает существующий черновик; при его отсутствии — `404`.
- PUT создаёт черновик (`201`) или обновляет переданные поля существующего (`200`).
- PATCH обновляет только переданные поля; сначала нужно создать черновик через PUT.
- Товар должен существовать. Аккаунт всегда JV, окружение берётся из настроек сервера;
  для одного товара сохраняются отдельные черновики Sandbox и Production.

Например, для дивана:

```json
{
  "title": "Graues Ecksofa mit Stoffbezug",
  "description": "Zweiteiliges Ecksofa mit grauem Polyesterbezug.",
  "category_id": "38208",
  "aspects": {
    "Produktart": ["Ecksofa"],
    "Anzahl der Teile": ["Zweiteilig"],
    "Farbe": ["Grau"],
    "Polsterstoff": ["100% Polyester"],
    "Breite": ["240 cm"],
    "Höhe": ["85 cm"],
    "Länge": ["160 cm"]
  },
  "image_urls": ["https://example.com/sofa.jpg"],
  "price_eur": "2099.00",
  "quantity": 5
}
```

Это пример, а не данные реального товара. Черновик разрешено сохранить пустым
или частично заполненным. `missing_requirements.fields` перечисляет незаполненные
основные поля, `missing_requirements.aspects` — обязательные характеристики.
Цена, если задана, должна быть положительной; количество допускает ноль.
Заголовок — до 80 символов, фотографии — до 24 HTTPS-ссылок с сохранением порядка.

При изменении категории или характеристик проверяются конечная категория,
известные имена, одиночные значения, ограничение длины и списки `SELECTION_ONLY`.
`FREE_TEXT` допускает собственное значение. При смене категории ранее заполненные
характеристики не удаляются молча: их нужно явно передать заново, либо передать `{}`.
Версия дерева и список обязательных характеристик сохраняются вместе с черновиком.
Обычное чтение и изменение названия не требуют загрузки справочника.

`missing_requirements` отражает только эти поля черновика и сохранённую версию схемы.
Пустой список **не означает готовность к публикации**: условные зависимости значений,
форматы отдельных характеристик, актуальность схемы, состояние товара, GPSR,
настройки продавца, доставка и политики потребуют проверки на этапе публикации.

Добавлена только таблица `ebay.EbayDraft` миграцией `0003_ebay_draft`.
Миграцию нужно применить обычным процессом развёртывания перед обращением к API.
Сохранение не меняет `Product`, остатки, EAN и листинги других маркетплейсов.
Ни inventory item, ни offer в eBay не создаются; очереди публикации не запускаются.

### Привязка политик и склада к черновику

Миграция `0004_draft_listing_settings` добавляет четыре необязательных поля только
в `EbayDraft`. Старые черновики сохраняются с пустыми ссылками, без массового обновления.
Добавились также соответствующие имена в `missing_requirements.fields`.

Выбранные владельцем настройки **JV Production / EBAY_DE**:

| Поле | Значение | Название |
| --- | --- | --- |
| `fulfillment_policy_id` | `266190688013` | 2 - 4 Wochen Depotum |
| `payment_policy_id` | `198328186013` | eBay-Zahlungsabwicklung |
| `return_policy_id` | `146898291013` | Standard Ruecknahme |
| `merchant_location_key` | `DE_88483` | Склад с индексом 88483, DE |

Владелец подтвердил фактический адрес: AEA GmbH & Co. KG, Am Flugplatz 28,
88483 Burgrieden, DE. В самой записи eBay сохранены только индекс и страна;
этот адрес в eBay автоматически не дописывается.

После применения миграции сохраните настройки в существующем черновике **на проде**:

```http
PATCH /api/v1/ebay/drafts/jv/<product_id>/
```

```json
{
  "fulfillment_policy_id": "266190688013",
  "payment_policy_id": "198328186013",
  "return_policy_id": "146898291013",
  "merchant_location_key": "DE_88483"
}
```

Если черновика ещё нет, создайте его через PUT по тому же адресу, с этим телом
или вместе с данными товара. Эти Production ID не подставляются автоматически
и не переносятся в Sandbox; там нужно выбирать собственные ресурсы Sandbox.

При добавлении или изменении непустой ссылки бэк получает токен JV **текущего
окружения** и читает выбранный ресурс через GET eBay. Политика должна принадлежать
этому продавцу, относиться к EBAY_DE и группе ALL_EXCLUDING_MOTORS_VEHICLES.
Склад должен быть ENABLED, иметь тип WAREHOUSE и минимально пригодный адрес.
Ошибки проверки возвращают `400`, ошибки чтения API eBay — `502`;
непроверенные ссылки не сохраняются. Политики и склады на стороне eBay не изменяются.

Обычный GET черновика, изменение названия и повторная отправка тех же ID
не вызывают API этих настроек. Пустая строка явно очищает ссылку без запроса к eBay.
Это остаётся неполным черновиком. Изменение или удаление политик другим сервисом
после сохранения здесь не отслеживается: перед публикацией потребуется новая проверка.

### Предпросмотр Inventory Item и Offer

Все товары проекта новые — в Inventory Item используется `condition: "NEW"`.
Дополнительного поля в товаре или миграции для этого не добавлено.

```http
GET /api/v1/ebay/drafts/jv/<product_id>/preview/
```

Для товара №69 после развёртывания:

```http
GET /api/v1/ebay/drafts/jv/69/preview/
```

Эндпоинт доступен менеджерам и администраторам. Он читает уже сохранённый черновик
JV текущего окружения; при его отсутствии возвращает `404`. Запросы записи к этому
маршруту не поддерживаются. GET не сохраняет даты, не создаёт записи, не обновляет
токены и не вызывает API eBay или загрузку изображений.

Ответ содержит:

- `preview_only: true` — сформированные запросы ещё никуда не отправлены;
- `inventory_item` — будущий PUT с URL, заголовками и телом: NEW, описание,
  название, фото в сохранённом порядке, характеристики и остаток;
- `offer` — будущий POST с категорией EBAY_DE, ценой EUR, количеством,
  выбранными политиками, складом, `FIXED_PRICE` и `GTC`;
- `sku` и `ean` — существующий `Product.ean_jv`; для товара №69 это `4071489789867`;
- `missing_regulatory_fields` — отсутствующие GPSR-контакты, независимо от заполненности остальных полей;
- `draft_complete` и `missing_requirements` — заполненность полей сохранённого черновика;
- `checks_not_performed` — проверки, которые ещё предстоят до отправки и публикации.

Цена передаётся строкой с двумя знаками после запятой. Количество `0` сохраняется
как ноль, а незаполненное количество не подменяется нулём. Для незаданной цены
`pricingSummary` не создаётся; для незаданного количества не создаются поля остатков.
Неполный черновик разрешено просматривать — `draft_complete` будет `false`.

`includeCatalogProductDetails: false` отключает подстановку описания из каталога eBay
в будущем Offer. Токены и заголовок Authorization в ответ не включаются.
Новые EAN не выделяются. SKU равен JV EAN и передаётся в Inventory Item также как
`product.ean: ["4071489789867"]`. Проверяются ASCII-цифры, длина EAN-8/EAN-13 и контрольная
цифра. При отсутствии валидного EAN `sku` пустой, URL Inventory Item равен `null`,
а `missing_requirements.fields` содержит `ean_jv`. Существующее распределение EAN не меняется.

Даже `draft_complete: true` не означает готовность к публикации. Здесь не выполняются
повторная проверка актуальных правил категории и состояния NEW, условий продавца,
склада и фактического местонахождения товара, доступности фото и требований GPSR.
Имена и содержимое запросов сверены с официальной
[схемой Inventory API](https://developer.ebay.com/api-docs/master/sell/inventory/openapi/3/sell_inventory_v1_oas3.json).
Для отправки без публикации добавлен отдельный POST `prepare/`, описанный ниже.

### GPSR-контакты в черновике

Поле `regulatory` сохраняется через существующий PUT/PATCH черновика. Формат соответствует
`offer.regulatory` Inventory API. Блок заменяется целиком, поэтому при последующем добавлении
производителя нужно также передать уже сохранённый `responsiblePersons`.

Пользователь подтвердил AEA как ответственную компанию в ЕС. Сохранение только этого
контакта разрешено. Отсутствующий производитель не блокирует создание неопубликованного
Offer и отображается в `missing_regulatory_fields` для проверки перед публикацией.
Не назначаем AEA производителем по адресу склада или по имени продавца.

```http
PATCH /api/v1/ebay/drafts/jv/69/
```

```json
{
  "regulatory": {
    "responsiblePersons": [
      {
        "companyName": "AEA GmbH & Co. KG",
        "addressLine1": "Am Flugplatz 28",
        "city": "Burgrieden",
        "postalCode": "88483",
        "country": "DE",
        "email": "info@jvmoebel.de",
        "phone": "+49 7392 9378440",
        "types": ["EU_RESPONSIBLE_PERSON"]
      }
    ]
  }
}
```

`manufacturer` содержит название, полный адрес и email либо contactUrl того же формата,
но без `types`. Для производителя за пределами ЕС дополнительно требуется ответственная
компания в ЕС. Отсутствующего производителя нельзя подменять ответственным.
`{ "regulatory": {} }` очищает GPSR-блок. Контакты проверяются целиком даже при PATCH.
Это проверка контактных данных, а не полная проверка GPSR: инструкции, предупреждения,
маркировка и прочие применимые требования проверяются отдельно перед публикацией.

### Создание неопубликованного Offer

После деплоя требуется применить миграцию `0005_ebaydraft_regulatory_ebayofferpreparation`.
Она добавляет только поле черновика и отдельную таблицу состояния отправки eBay.

```http
POST /api/v1/ebay/drafts/jv/69/prepare/
Content-Type: application/json

{"confirm_stock_location": true}
```

Это реальная запись в eBay текущего окружения! Подтверждение означает, что товар
действительно находится на выбранном `merchant_location_key`, а не просто что известен
адрес склада. Для №69 в исходном товаре был указан Bursa: наличие в Burgrieden необходимо
подтвердить отдельно. Не отправлять `true` до проверки фактического наличия.

Проверки и порядок:

1. Локальные обязательные поля, существующий EAN, корректность введённых GPSR-контактов, одобренный и доступный
   товар, положительное количество не выше суммы остатков вариантов, описание до 4000 символов.
   Недостающие GPSR-контакты не блокируют этот этап подготовки; подставные данные не добавляются.
   eBay может самостоятельно отклонить запрос — такой отказ сохраняется как ошибка API.
2. Характеристики по доступной схеме категории, обязательные аспекты; условия NEW по
   `GET /sell/metadata/v1/marketplace/EBAY_DE/get_item_condition_policies?filter=categoryIds:{38208}`.
3. Повторное чтение трёх выбранных политик и склада именно подключённого продавца.
4. `GET /sell/inventory/v1/offer?sku=<EAN>` без ограничения marketplace/формата:
   любой существующий Offer запрещает перезапись Inventory Item. Неполный ответ также блокирует отправку.
5. `GET /sell/inventory/v1/inventory_item/<EAN>`: существующая запись, созданная вне этой
   подготовки, не перезаписывается и автоматически не присваивается проекту.
6. `PUT /sell/inventory/v1/inventory_item/<EAN>` и затем `POST /sell/inventory/v1/offer`.
   После каждого этапа сохраняется состояние, после успеха — `offer_id` и отпечаток данных.

`POST .../prepare/` не вызывает publish, withdraw или delete и не меняет Product,
его EAN, фотографии FTP, общую логику остатков или другие маркетплейсы.

Состояние доступно также без внешних запросов:

```http
GET /api/v1/ebay/drafts/jv/69/prepare/
```

- `prepared` — Offer создан; `offer_id` сохранён. Повтор того же POST возвращает сохранённый
  результат без записи в eBay. Это локальный результат подготовки, не актуальная проверка внешнего Offer.
- `failed` — проверки или явный отказ API; `inventory_confirmed` показывает, успели ли создать Inventory Item.
- `uncertain` — запись могла выполниться, но достоверного результата нет. Повтор заблокирован (409).
- `processing` — операция выполняется. После аварийного завершения она также не перезапускается автоматически.

При `uncertain`/зависшем `processing` сначала вручную сверить eBay по SKU и локальные этапы;
не очищать состояние и не повторять POST вслепую. Автоматической сверки/присвоения чужого Offer нет.
HTTP-статус, числовые errorId, метод/путь запроса, сообщения `message`/`longMessage`
и уточнения из `parameters` (включая `reason`)
сохраняются без сырого тела ответа. Токен, отражённые значения GPSR-контактов,
email и ссылки удаляются из сообщений; длина сообщений ограничена.
Черновик заблокирован для редактирования при `processing`/`uncertain`.
Изменение данных после успешной подготовки применяется через отдельный `POST update/`,
описанный ниже. `POST prepare/` не создаст дубль и вернёт 409, если отпечаток изменился.

`publication_performed: false` означает, что этот код не публиковал Offer.
Внешние изменения другими приложениями этим флагом не проверяются.

Ограничения: доступность/размеры фотографий, условные зависимости значений аспектов и полная
проверка нормативных требований ещё не проверяются. Проверка наличия SKU и PUT не атомарны
на стороне eBay — не запускать параллельную работу другого приложения с тем же SKU.
Удаление товара в проекте сохраняет прежнее поведение: локальные записи каскадно удаляются,
но созданные ресурсы eBay не удаляются. После этого повторная подготовка откажет при занятом SKU.

### Обновление существующего неопубликованного Offer

Сначала изменить локальный черновик через прежний PATCH, затем посмотреть preview.
Этот PATCH по-прежнему не изменяет eBay или основной Product.
Для применения сохранённых данных к eBay добавлен отдельный маршрут:

```http
POST /api/v1/ebay/drafts/jv/69/update/
Content-Type: application/json

{"confirm_stock_location": true}
```

`update/` использует сохранённые SKU и offerId, никогда не вызывает создание нового Offer.
Менеджер не передаёт offerId извне. В Production JV уже проверено создание Offer
`1160767892016` для товара №69 и безопасное повторение `prepare/`; новое обновление
на этом Offer пока не проверялось. Новая миграция для `update/` не требуется.

Перед изменениями повторно проверяются заполненность черновика, существующий EAN,
остаток, актуальные условия NEW, политики и склад. Отсутствие производителя остаётся
предупреждением перед публикацией; введённые GPSR-контакты проверяются.

Затем выполняются:

1. `GET /sell/inventory/v1/offer?sku=<EAN>`: должен быть ровно один Offer,
   без следующих страниц; другой Offer того же SKU блокирует операцию.
2. `GET /sell/inventory/v1/offer/<offerId>`: проверяются offerId, SKU, EBAY_DE,
   FIXED_PRICE, статус UNPUBLISHED, отсутствие listing и даты запланированного запуска.
   Неполный ответ или опубликованное/ранее связанное с listing предложение блокируются.
3. `GET /sell/inventory/v1/inventory_item/<EAN>`: проверяются существование и SKU;
   Inventory Item группы вариантов этим маршрутом не обновляется.
4. `PUT /sell/inventory/v1/inventory_item/<EAN>` с данными черновика.
5. Повторяются обе проверки Offer из пунктов 1–2, затем
   `PUT /sell/inventory/v1/offer/<offerId>` с актуальными полями черновика.

Оба PUT полностью заменяют соответствующие ресурсы API. Поэтому код читает прежние
настройки, сохраняет дополнительные поддерживаемые поля eBay (например, налоговые
настройки Offer и вес/габариты посылки), исключает read-only поля и накладывает
значения черновика. Списки и `aspects` заменяются целиком; вложенные объекты объединяются.
Поля, отсутствующие в черновике, сохраняются: например, `{ "regulatory": {} }`
очистит локальный блок, но не удалит ранее сохранённые GPSR-контакты eBay через update.
При неизвестных полях ответа на верхнем уровне запись запрещена вместо молчаливой потери данных.

Успех возвращает прежний `offer_id`, `status: prepared`, пустую ошибку и
`publication_performed: false`. Обновлённый отпечаток сохраняется только после обоих
успешных PUT. Тот же `update/` можно повторить: он вновь проверит eBay и применит данные
к тем же ресурсам, не создавая нового Offer.

Состояние читается прежним `GET .../prepare/`. После явного отказа сохраняется `failed`,
ID остаётся прежним. Если Inventory Item уже изменён, это явно указано в `last_error`:
откат автоматически не выполняется. При таймауте записи сохраняется `uncertain`, повтор
и редактирование черновика блокируются до сверки результата. Не сбрасывать состояние вслепую.

Проверки после деплоя:

- Сделать `PATCH /api/v1/ebay/drafts/jv/69/` с согласованным изменением, затем GET preview.
- Один POST update с подтверждением склада; ожидать прежний `offer_id: 1160767892016`.
- Проверить статус и сохранение прежнего ID при повторе.
- На моках/Sandbox проверить опубликованный Offer, другой Offer того же SKU,
  смену состояния между PUT, ошибки и таймауты. Не публиковать реальный товар для проверки защиты.

Ограничение: проверки GET и PUT не атомарны на стороне eBay. Не публиковать и не менять
этот SKU параллельно из кабинета или другого приложения. Между двумя PUT возможен
частичный результат; `prepared` означает успешную отправку двух PUT, а не полную готовность к публикации.
Фото и полная проверка GPSR остаются отдельным этапом. Обновление затрагивает только eBay;
основной Product, EAN, фотографии FTP и другие маркетплейсы не изменяются.

Имена методов и правила полного замещения сверены с
[официальной схемой Inventory API](https://developer.ebay.com/api-docs/master/sell/inventory/openapi/3/sell_inventory_v1_oas3.json).
