# Авторизация eBay и уведомления об удалении аккаунта

На этом этапе реализовано подключение продавцов JV, XL и Depotum к eBay.
Публикация реализована только для Depotum. SKU и EAN берутся из существующего Product.ean_jv; новые номера не выделяются.
Ни один из этих эндпоинтов не удаляет аккаунт на eBay.

## Настройки сервера

Укажите следующие значения в окружении сервера. Не коммитьте секреты.

| Настройка | Stage | Прод |
| --- | --- | --- |
| `EBAY_ENVIRONMENT` | `sandbox` | `production` |
| `EBAY_PUBLIC_BASE_URL` | `https://stage.benimdepom.info` | `https://benimdepom.info` |
| App ID (OAuth Client ID) | `EBAY_SANDBOX_APP_ID` | `EBAY_PROD_APP_ID` |
| Cert ID (OAuth Client Secret) | `EBAY_SANDBOX_CERT_ID` | `EBAY_PROD_CERT_ID` |
| `EBAY_RUNAME` | OAuth RuName для Sandbox | OAuth RuName для Production |
| `EBAY_TOKEN_ENCRYPTION_KEY` | Отдельный ключ Fernet | Другой отдельный ключ Fernet |
| `EBAY_NOTIFICATION_VERIFICATION_TOKEN` | Случайный токен подтверждения | Другой случайный токен подтверждения |

`EBAY_CLIENT_ID` и `EBAY_CLIENT_SECRET` — внутренние настройки Django: они берутся
из переменных выбранного окружения. Добавлять их в `.env` не нужно.
Существующие `EBAY_SANDBOX_DEV_ID` и `EBAY_PROD_DEV_ID` можно оставить в `.env`;
текущая авторизация через REST OAuth не использует Dev ID.
Ключи приложения общие для JV, XL и Depotum. Каждый продавец проходит авторизацию
отдельно и получает собственные токены, которые сохраняются в системе.

Создайте ключ шифрования локально:

```sh
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Создайте токен подтверждения адреса уведомлений локально:

```sh
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Храните ключ шифрования в безопасном месте и сохраняйте его резервную копию.
Замена ключа сделает уже сохранённые токены нечитаемыми.
Токен подтверждения уведомлений — отдельное значение, а не Client Secret или токен доступа eBay.
Установите зависимости, примените миграции и выкатите бэкенд перед настройкой адресов в eBay.

## Настройка кабинета eBay Developer

Для Production откройте **Alerts & Notifications → Marketplace Account Deletion** и заполните:

- **Notification endpoint:** `https://benimdepom.info/api/v1/ebay/account-deletion/`
- **Verification token:** точное значение `EBAY_NOTIFICATION_VERIFICATION_TOKEN` на проде.
- **Alert email:** рабочий адрес компании, на котором отслеживаются уведомления.

При сохранении eBay автоматически отправляет проверочный GET-запрос с `challenge_code`.
К этому моменту эндпоинт должен быть доступен публично.
GET возвращает SHA-256 ответ на проверку и не меняет данные.
POST проверяет `X-EBAY-SIGNATURE` публичным ключом eBay, затем удаляет соответствующее
локальное подключение eBay и незавершённые попытки авторизации.
Пользователи BENIM, товары и данные остальных маркетплейсов не удаляются.
Содержимое уведомлений и пользовательские токены не сохраняются в логах или таблицах входящих уведомлений.
Повторное подлинное уведомление безопасно: если подключение уже отсутствует, удалять нечего.
После добавления хранения листингов и заказов eBay обработчик потребуется дополнить
удалением связанных с аккаунтом данных.

В разделе **User Tokens** создайте RuName с поддержкой OAuth.
В поля **Auth Accepted URL** и **Auth Declined URL** укажите:

- Sandbox: `https://stage.benimdepom.info/api/v1/ebay/oauth/callback/`
- Production: `https://benimdepom.info/api/v1/ebay/oauth/callback/`

Также укажите адрес опубликованной политики конфиденциальности BENIM.
Скопируйте идентификатор RuName в `EBAY_RUNAME`.
Именно этот идентификатор отправляется в параметре `redirect_uri`, а не адрес callback.

## Подключение продавцов

От имени авторизованного менеджера BENIM отправьте запрос:

```http
POST /api/v1/ebay/oauth/start/
Content-Type: application/json
Authorization: Bearer BENIM_MANAGER_ACCESS_TOKEN

{"account":"depotum"}
```

Вместо `BENIM_MANAGER_ACCESS_TOKEN` подставьте токен доступа менеджера BENIM.
Откройте полученный `authorization_url` в браузере и разрешите доступ от соответствующего продавца eBay.
На stage используйте тестового продавца Sandbox, на проде — реального продавца.
Для текущей публикации нужен только Depotum. Существующие подключения JV/XL сохраняются; их токены не используются для публикации Depotum.

Для определения неизменяемого ID продавца запрашивается разрешение
`https://api.ebay.com/oauth/api_scope/commerce.identity.readonly`.
Identity API использует домен `apiz.ebay.com` (Sandbox: `apiz.sandbox.ebay.com`);
запросы OAuth-токенов используют обычный домен `api`.
После изменения набора разрешений начните авторизацию заново через `/oauth/start/`:
обновление старой страницы callback не выдаст токен с новыми разрешениями.

Callback возвращает подтверждение подключения без раскрытия токенов.
Внутренняя функция `get_access_token` обновляет истекающие токены при обращении к ней.
`GET /api/v1/ebay/connections/` возвращает менеджеру список подключений и сроки действия токенов,
но не сами токены.
Одного пользователя eBay нельзя привязать к нескольким аккаунтам в одном окружении.

## Проверка готовности аккаунта

После подключения JV вызовите от имени менеджера:

```http
GET /api/v1/ebay/readiness/?account=jv
Authorization: Bearer BENIM_MANAGER_ACCESS_TOKEN
```

В Swagger эндпоинт находится в разделе **eBay**. Передайте `account=jv`.
Проверка использует текущее окружение сервера и площадку `EBAY_DE`.
Токен продавца берётся из сохранённого подключения; передавать его вручную не нужно.
Если токен истекает, бэкенд обновляет его через refresh token и сохраняет новое значение.

Эндпоинт читает регистрацию и месячные лимиты, участие в Business Policies,
политики доставки, оплаты и возврата для Германии, а также все страницы складов.
Товары и настройки продавца на eBay не изменяются.

| Поле ответа | Значение |
| --- | --- |
| `checks_complete` | Все запросы к eBay завершились успешно |
| `ready_for_listing_setup` | Получены базовые настройки для подготовки листинга |
| `seller_registration_completed` | Завершена ли регистрация продавца |
| `selling_limit` | Лимиты количества и суммы из eBay; `null`, если данные не получены или лимит не указан |
| `business_policies_enabled` | Подключена ли программа `SELLING_POLICY_MANAGEMENT` |
| `policies` | Идентификаторы и названия политик; `applicable_to_furniture` показывает применимость к обычным товарам на `EBAY_DE` |
| `inventory_locations` | Ключи складов, состояние и краткий адрес; `usable` учитывает доступность склада и наличие адреса |
| `missing_requirements` | Полученные от eBay настройки, которых не хватает |
| `errors` | Ошибки отдельных запросов: HTTP-код, а также `errorId` и `message`, если eBay их вернул |

Успешный HTTP-ответ `200` может содержать неполный отчёт: проверяйте `checks_complete` и `errors`.
Пустой список означает отсутствие ресурсов, а `null` при ошибке означает, что данные не удалось получить.
При частичной ошибке бэкенд сохраняет в ответе остальные успешно проверенные разделы.
Диагностика включает не более трёх ошибок eBay и до 500 символов каждого сообщения.
Полное тело ответа, параметры ошибки и заголовки авторизации не возвращаются;
совпадения с токеном доступа в сообщениях скрываются.
Склады читаются с пагинацией; адрес следующей страницы из ответа eBay не используется напрямую.
На обход отводится 45 секунд до запуска следующего запроса; уже начатый запрос может завершиться позже
в пределах своего таймаута. Автоматические повторы в этой ручной проверке отключены.

`ready_for_listing_setup=true` не гарантирует публикацию конкретного товара и не проверяет
достаточность лимита для его цены и количества. Категория, атрибуты, изображения, условия
доставки и остальные требования предложения проверяются на следующих этапах.
Значения Sandbox не определяют ограничения реального продавца в Production.

## Категории и характеристики EBAY_DE

Справочники доступны только менеджерам и администраторам, в разделе **eBay** Swagger.
В Sandbox используются локальные JSON из `data/ebay/sandbox/`, ключи eBay не нужны.
В Production используется токен приложения (`client_credentials`) по ключам Production.
OAuth-подключение продавца, завершённая регистрация, политики и склад
для чтения справочников не нужны. Дополнительные env-переменные не требуются.

### Навигация по категориям

```http
GET /api/v1/ebay/catalog/categories/
```

Без параметров в Sandbox возвращает категорию мебели `Möbel` (`3197`),
в Production — верхний уровень дерева Германии. В каждом элементе
`categories` есть `id`, `name` и `is_leaf`. Для просмотра следующего уровня:

```http
GET /api/v1/ebay/catalog/categories/?parent_id=<id из предыдущего ответа>
```

`parent` описывает выбранную категорию; у конечной категории список детей пустой.
В ответе также есть `environment`, `marketplace_id`, `category_tree_id`
и `category_tree_version`. Неизвестная категория возвращает `404`, неверный
формат ID — `400`. Полное дерево наружу не передаётся.

### Характеристики конечной категории

```http
GET /api/v1/ebay/catalog/categories/<category_id>/aspects/
```

Принимается ID с `is_leaf=true`. Родительская категория возвращает `400`.
Ответ содержит:

- `category` — выбранную категорию;
- `aspects` — исходные характеристики eBay, включая `aspectConstraint`,
  `aspectValues`, зависимости и прочие доступные поля;
- `required_aspects` — названия, у которых `aspectConstraint.aspectRequired=true`;
- окружение, площадку, ID и версию дерева.

Рекомендуемую характеристику нельзя считать обязательной только из-за
`aspectUsage=RECOMMENDED`: смотреть нужно на `aspectRequired`.
Получение схемы не сохраняет категорию или значения в товаре и не проверяет
заполненный товар. Это отдельный этап интеграции.

### Кеш и Sandbox

В Sandbox `categories.json` содержит ветку мебели; `aspects/<category_id>.json` —
характеристики её конечных категорий. Внешние запросы и получение токена не выполняются.
Категории вне этой ветки возвращают `404`. Отсутствующий или повреждённый JSON
возвращает ошибку; отсутствующие файлы и несовпадение версии характеристик с деревом — `503`.
Автоматического перехода на API нет. Файлы включаются в Docker-образ из `data/ebay/`.
Локальные данные кешируются на 24 часа по пути, размеру и времени изменения файла:
обновлённый файл читается без ожидания истечения кеша. Сам каталог автоматически
не скачивается; снимок нужно обновлять отдельно.

В Production поведение сохранено: дерево и характеристики кешируются на 24 часа; ключ характеристик включает
версию дерева. Токен приложения переиспользуется до срока обновления.
Кеши разделены по окружению и Client ID. Ошибки и повреждённые ответы
не сохраняются как пустые успешные справочники. На первом обращении загружается
полное дерево для серверной навигации, поэтому оно медленнее последующих.

Автоматические повторы GET для этих ручных запросов отключены;
таймаут внешнего GET — 5 секунд на соединение и 10 секунд на чтение.
Время первого обращения также включает получение токена и ID дерева.

`getCategorySuggestions` не используется: официальная документация предупреждает
о шаблонных названиях в Sandbox. Нет автоматического переключения на Production.
Здесь реализована навигация по дереву, а не поиск по ключевым словам.

Источники: [Taxonomy API](https://developer.ebay.com/api-docs/commerce/taxonomy/static/overview.html),
[getCategorySuggestions и ограничения Sandbox](https://developer.ebay.com/api-docs/master/commerce/taxonomy/openapi/3/commerce_taxonomy_v1_oas3.json).

## Товары: только Depotum

Для товара доступны следующие адреса. Все доступны только менеджеру:

| Адрес после /api/v1/ebay/ | Методы | Назначение |
| --- | --- | --- |
| drafts/depotum/<product_id>/ | GET, PUT, PATCH | Прочитать, создать или изменить локальный черновик |
| drafts/depotum/<product_id>/prepare/ | GET, POST | Прочитать состояние; создать или обновить неопубликованное предложение eBay |
| drafts/depotum/<product_id>/publish/ | GET, POST | Проверить готовность и получить hash; явно подтвердить реальную публикацию |
| drafts/depotum/<product_id>/listing/ | GET, PUT, DELETE | Прочитать ресурсы eBay; обновить активное объявление; снять с продажи |

Удалены все маршруты drafts/jv/ и отдельные preview/, remote/, update/ у Depotum.
Сохранённые подключения, черновики, Offer и опубликованные объявления не удаляются.
Существующие внешние клиенты удалённых адресов нужно перевести на эту последовательность.
Frontend в проекте эти маршруты не вызывает.

### 1. Сохранить черновик

PUT /api/v1/ebay/drafts/depotum/69/ создаёт черновик; PATCH того же адреса
меняет переданные поля. GET возвращает черновик и missing_requirements.
Передавайте title, description, image_urls, price_eur, quantity, category_id, aspects,
fulfillment_policy_id, payment_policy_id, return_policy_id, merchant_location_key и regulatory.
Набор обязательных характеристик определяется категорией; пропуски возвращаются в missing_requirements.
regulatory при PATCH заменяется целиком: передавайте manufacturer и responsiblePersons вместе.

Политики и склад должны принадлежать Depotum и подходить EBAY_DE. Их ID можно получить
через GET readiness/?account=depotum. Чужие ID JV не переносятся автоматически.
Все товары отправляются с condition=NEW, SKU равен существующему ean_jv.
В Offer по умолчанию отправляется `tax: {"vatPercentage": 19.0}` при создании и
обновлении неопубликованного предложения. `price_eur` передаётся как окончательная
цена с включённым НДС: бэкенд не прибавляет к ней ещё 19%.
`applyTax` не включается для НДС: это отдельная настройка таблицы sales tax.
Уже опубликованные объявления автоматически не меняются.
Product, EAN, складские остатки и данные других маркетплейсов не меняются.

### 2. Подготовить или применить изменения

POST /api/v1/ebay/drafts/depotum/69/prepare/

~~~json
{"confirm_stock_location": true}
~~~

Подтверждайте фактическое наличие на выбранном складе. При первом вызове создаются
Inventory Item и неопубликованный Offer. После изменения черновика тот же POST
обновляет сохранённый Offer с прежним ID. Неизменённый успешно подготовленный черновик
возвращает сохранённый результат без повторных запросов записи.

Состояния processing/uncertain блокируют повтор до ручной сверки: запрос мог дойти до eBay.
Отсутствующий локальный черновик не подменяется черновиком другого аккаунта.
Опубликованный Offer этим методом не обновляется: для него возвращается 409.
GET prepare/ показывает status, SKU, offer_id, listing_id и last_error без записи в eBay.

### 3. Проверить и опубликовать

GET /api/v1/ebay/drafts/depotum/69/publish/

Возвращает ready, blocking_reasons, manual_checks и preview_hash. Отдельно вызывать
preview/ или remote/ больше не нужно: сравнение Inventory Item и Offer с черновиком
выполняется внутри проверки готовности.

После ready=true и ручной проверки склада, фотографий, документов и предупреждений:

POST /api/v1/ebay/drafts/depotum/69/publish/

~~~json
{
  "confirm_publication": true,
  "confirm_stock_location": true,
  "preview_hash": "<hash из GET publish/>"
}
~~~

Это реальная публикация с возможными сборами eBay. Успех: status=published,
publication_performed=true и непустой listing_id. Повтор успешной публикации возвращает
сохранённый listing_id без второго publish. После изменения черновика сначала POST prepare/,
затем GET publish/: старый hash не разрешает публикацию новых данных.

### Какие проверки остались и зачем

- Права менеджера и токен нужного аккаунта: не разрешать публикацию чужим пользователем или на JV/XL.
- Обязательные поля, характеристики категории, корректный EAN, положительный остаток,
  одобренный доступный Product: не отправлять неполную или неразрешённую карточку.
- Политики, действующий склад, регистрация продавца, разрешённое NEW: проверять текущую конфигурацию.
- GPSR manufacturer и при необходимости responsiblePersons: не пропускать незаполненные контакты.
- Совпадение удалённых данных и hash: не публиковать старую цену, описание или количество.
- Наличие чужих Offer, группировок, статус UNPUBLISHED и блокировки БД: не перезаписывать
  чужой ресурс, не создавать дубли и не запускать конкурентные операции.
- HEAD фото только на настроенном публичном HTTPS media host без редиректов:
  проверять доступность и не разрешать запросы к произвольным внутренним адресам.
- Не повторять автоматически неопределённый результат записи: избегать двойной публикации.

POST publish повторяет проверки: результат предварительного GET может устареть.
Вызовы eBay не атомарны; не редактируйте и не публикуйте один SKU параллельно в другом приложении.
Качество/размеры фото, фактический склад и документы безопасности автоматически не подтверждаются.
Лимиты продавца и окончательное принятие объявления проверяет eBay при publish.
Обновление активных объявлений и снятие с продажи описаны ниже.

## Управление опубликованным объявлением Depotum

### Получение текущих данных

`GET /api/v1/ebay/drafts/depotum/69/listing/` выполняет:

- `GET /sell/inventory/v1/inventory_item/<sku>`;
- `GET /sell/inventory/v1/offer/<offerId>`.

Возвращает полные `inventory_item` и `offer`, время `checked_at`, `remote_status`,
`listing_status`, `remote_listing_id` и `preparation` (локальное состояние).
Это все поля этих двух ресурсов: описание, фото, характеристики, остаток, цена, НДС,
политики, GPSR и данные листинга, доступные в Inventory API. Заказы, аналитика и полный
HTML страницы eBay не входят в эти ресурсы. ID ресурсов берутся из нашей сохранённой
привязки, а не из произвольных параметров запроса. Данные читаются с токеном Depotum.

При 404 ресурса eBay соответствующее поле равно null. Локальные статусы GET не исправляет
и неопределённый результат не сбрасывает. Это позволяет сверить таймаут с реальными данными.

### Обновление активной публикации

Сначала сохраните желаемые поля через PATCH локального черновика, затем:

~~~http
PUT /api/v1/ebay/drafts/depotum/69/listing/
Content-Type: application/json

{"confirm_update": true, "confirm_stock_location": true}
~~~

PUT использует сохранённый черновик, не принимает произвольные поля eBay в теле.
Он реально меняет опубликованное объявление: название, описание, фотографии, характеристики,
цену, положительное количество, политики, склад, GPSR, HTML-описание и НДС 19%.
Для применения нового шаблона/НДС можно выполнить PUT без изменения локального текста.
Offer ID и listing ID сохраняются. Создание, publish, withdraw и DELETE ресурсов не вызываются.

Перед записью проверяются товар, EAN, склад/политики, NEW, GPSR, фото и соответствие
активному сохранённому listing ID. Для общего Inventory Item допускается только один
известный Offer данного SKU, без групп вариантов. Незнакомые поля не удаляются молча.
Полные PUT сохраняют прочие поддержанные настройки eBay; вычисляемое allocationByFormat
не отправляется обратно. Между двумя PUT повторно проверяется активный listing ID.

Успех возвращает `status: published` и прежний `listing_id`. После PUT получите GET listing/
и проверьте актуальные данные. Изменения также ограничены правилами eBay для редактирования
действующих объявлений; их отказ возвращается клиенту, объявление автоматически не снимается.

### Снятие с продажи

~~~http
DELETE /api/v1/ebay/drafts/depotum/69/listing/?confirm_withdrawal=true
~~~

В Swagger укажите `product_id` и query-параметр `confirm_withdrawal=true`, без тела запроса.
Прежнее JSON-тело `{"confirm_withdrawal": true}` поддерживается для совместимости.
Без подтверждения или при false снятие не выполняется.

Этот DELETE вызывает **POST /sell/inventory/v1/offer/<offerId>/withdraw**, а не
deleteOffer/deleteInventoryItem. eBay завершает активное объявление и переводит Offer
в UNPUBLISHED, сохраняя сам Offer и Inventory Item. Локально записывается `status: withdrawn`.
Старый listing_id сохраняется для истории и сверки; `publication_performed: true` означает,
что публикация когда-то выполнялась, а не что объявление сейчас активно.
Товар BENIM, EAN, остатки других каналов и FTP-фотографии не удаляются.
Повтор успешного DELETE не отправляет второй withdraw.

Физическое удаление ресурсов eBay не реализовано. Снятый Offer можно явно выставить
снова через существующий publish/; новый Offer при этом не создаётся.

### Повторное выставление после снятия

1. При необходимости измените локальный черновик через PATCH. Если данные или шаблон
   изменились, выполните POST prepare/ с `{"confirm_stock_location": true}`: он обновит
   тот же снятый Offer. Без изменений этот шаг не обязателен.
2. Выполните `GET /api/v1/ebay/drafts/depotum/69/publish/` и проверьте ready/blocking_reasons.
3. При ready=true отправьте POST на тот же publish/:

~~~json
{
  "confirm_publication": true,
  "confirm_stock_location": true,
  "preview_hash": "<новый hash из GET publish/>"
}
~~~

Hash привязан к последнему listing_id: старый POST первой публикации после снятия
отклоняется с 409, даже если карточка не менялась. Повторное выставление требует явного
подтверждения с новым hash. Проверяются фактический UNPUBLISHED, единственный известный
Offer данного SKU, совпадение удалённых полей, GPSR, фото, политики, склад и NEW.
Если eBay возвращает историю listing, допускается только ENDED с нашим прежним ID.
Активный или чужой listing запрещён; при неопределённом предыдущем результате повтор блокируется.

Успешный `POST /sell/inventory/v1/offer/<offerId>/publish` сохраняет тот же offer_id и
**новый listing_id**, заменяя прежний ID локально. Старое объявление не активируется:
создаётся новая публикация. Повтор успешного POST возвращает уже сохранённый новый ID
без второго вызова publish. Таймаут или возврат старого ID фиксируются как uncertain,
с прежним listing_id для сверки; автоматически повторять такой запрос нельзя.
GET listing/ позволяет прочитать результат из eBay, не снимая блокировку автоматически.

Дополнительных маршрутов и миграций для повторного выставления нет. Операция может
привести к новым сборам eBay. Во время реализации реальные снятия/публикации не выполнялись.

### Ошибки и деплой

Изменения сериализуются блокировкой того же черновика; редактирование во время операции
блокируется. При таймауте записи, неопределённом ответе или частичном обновлении фиксируется
`uncertain`; повторные изменения запрещены до ручной сверки. При однозначном отказе до
успешного первого PUT сохраняется published с last_error. Два запроса PUT не являются
транзакцией eBay, отката нет. Не редактируйте тот же товар параллельно в стороннем приложении.

Перед использованием нужна миграция `0007_offer_withdrawn` (`python manage.py migrate`).
Тесты добавлены с моками без запуска. При реализации настоящие объявления не изменялись
и не снимались с продажи.

Источники: [управление предложениями](https://developer.ebay.com/api-docs/sell/static/inventory/managing-offers.html),
[управление объявлениями и различия withdraw/delete](https://developer.ebay.com/develop/guides/sell/listing-management).

## HTML-описание Depotum

В черновике `description` остаётся обычным текстом (до 4000 символов для Inventory Item).
В `product.description` Inventory Item отправляется тот же текст. Для `offer.listingDescription`
автоматически формируется HTML через `description.render_listing_description` и шаблон
`templates/ebay/listing_description.html`. Отдельных полей и маршрутов нет.

В HTML включаются название, EAN, состояние NEW, описание, характеристики и фотографии
из `image_urls`: большая фотография и переключение по миниатюрам с помощью CSS `:target`.
Вкладки используют radio/`:checked`, без JavaScript. На телефоне миниатюры располагаются
горизонтально с прокруткой; свайп по большому изображению не реализован.
CSS находится внутри описания, внешние шрифты, стили и скрипты eBay/Afterbuy не используются.
Из исходного фирменного шаблона сохранены три баннера на productron.de/AfterbuyWebTag:
webtag1_jv_10122.png (сверху), webtag2_jv_women21321.png (слева) и webtag3_jv_3330.png (снизу).
Их текст/брендинг берётся из самих изображений; они не входят в image_urls товара.
На узком экране боковой баннер располагается после товарного блока.
Вкладки: Produktdetails, Farben, Lieferzeiten, Zahlung, Optional. Характеристики оформлены
текстовыми блоками Artikel-Nr./Maße/Farbe/материалы и остальные параметры, без таблицы.
Данные экранируются, URL фотографий допускаются только HTTPS без credentials.
Вкладки доставки/возврата/оплаты отсылают к условиям текущего предложения eBay:
сроки, предоплата, способы оплаты и дополнительные услуги из чужого шаблона не копируются.

Изменение шаблона меняет payload_hash. Для ранее подготовленного, но неопубликованного
Offer выполните POST prepare/, затем GET publish/ для нового hash и подтвердите публикацию.
Уже опубликованный listing 860068312907 автоматически не изменяется; для применения HTML
вызовите PUT listing/ с явным подтверждением. После деплоя ещё нужна визуальная проверка
в реальном описании eBay, особенно в мобильном приложении.

## Комплекты с размерами отдельных частей

Комплект продаётся одним SKU/EAN, с общей ценой и количеством полных комплектов.
Обязательные Breite/Länge/Höhe содержат размеры основного предмета.
Дополнительные размеры передаются в том же `aspects`, с именами `Maße ...`:
до 40 символов в имени, одно непустое значение до 65 символов. Остальные неизвестные
имена по-прежнему отклоняются; правила стандартных аспектов категории сохраняются.
Проверка применяется и при сохранении, и перед отправкой в eBay.

Пример для подтверждённого состава товара 42 — PATCH существующего черновика
`/api/v1/ebay/drafts/depotum/42/` (aspects заменяется целиком):

~~~json
{
  "aspects": {
    "Produktart": ["Sofa Set"],
    "Polsterstoff": ["Stoff"],
    "Farbe": ["Orange Beige"],
    "Breite": ["105 cm"],
    "Länge": ["254 cm"],
    "Höhe": ["90 cm"],
    "Anzahl der Teile": ["Dreiteilig"],
    "Maße Hauptsofa (B × L × H)": ["105 × 254 × 90 cm"],
    "Maße Sessel (B × L × H)": ["105 × 71 × 100 cm"],
    "Maße weiteres Sofa (B × L × H)": ["105 × 254 × 100 cm"]
  }
}
~~~

Значения из `Product.set_parts` переносятся в черновик явно: описание части может быть
на другом языке, поэтому имена предметов и порядок осей подтверждает менеджер.
При изменении исходного товара сохранённые размеры объявления не меняются автоматически.
В Inventory Item эти поля уходят в `product.aspects`, а в HTML выводятся в блоке Maße
вместо общего заголовка комплекта с размерами одного предмета. Имена и значения экранируются.
Без дополнительных размеров прежний HTML остаётся прежним.
Новых маршрутов, полей БД, миграций и вариаций для этого нет.

## Служебные адреса

OAuth start/callback и connections нужны для подключения и проверки токенов;
readiness — для политик, склада и регистрации продавца; catalog/categories и
catalog/categories/<category_id>/aspects — для выбора категории и характеристик.
account-deletion нужен для обязательных уведомлений eBay и остаётся по прежнему адресу.
Они не являются отдельными этапами публикации каждого товара.
