# Работа с товарами eBay: создание, чтение, обновление и снятие

Инструкция для разработчика: от получения доступов до создания, редактирования и снятия объявлений.

Материал получен от другого сервиса и описывает рекомендуемый сценарий интеграции, а не уже реализованные возможности BENIM.

Инструкция основана на официальной документации eBay. Примеры ориентированы на **eBay Germany (EBAY_DE)**, **EUR** и продажу по фиксированной цене.

## 1. Что понадобится

Необходимо подготовить:

| Что | Для чего |
| --- | --- |
| Аккаунт продавца eBay | От его имени будут размещаться объявления |
| Аккаунт eBay Developers Program | Получение ключей приложения |
| Production keyset | Работа с настоящими объявлениями |
| Sandbox keyset и тестовый продавец | Проверка интеграции без реальных продаж |
| OAuth redirect / RuName | Подключение аккаунта продавца |
| Серверная часть приложения | Хранение токенов и выполнение запросов |

Ключи Sandbox и Production создаются отдельно. Начать можно через eBay Developers Program.
**Важно:** для Production необходимо настроить уведомления об удалении аккаунтов eBay либо получить предусмотренное eBay освобождение от этой обязанности. Нельзя просто указать фиктивный webhook, который ничего не обрабатывает. Требования eBay.

## 2. Какие API использовать

Для новой интеграции основной путь — Sell Inventory API.

| API | Назначение |
| --- | --- |
| Inventory API | Товары, остатки, предложения, публикация и снятие |
| Account API | Политики доставки, оплаты и возврата |
| Taxonomy API | Категории и характеристики товаров |
| Metadata API | Допустимые состояния и ограничения категории |
| Trading API | Отдельный путь для существующих Legacy-объявлений |

Рекомендация: начать с Inventory API для новых объявлений, а поддержку старых объявлений реализовать отдельно. Управление объявлениями.

## 3. Как получить авторизацию

Логина и пароля продавца недостаточно. Приложение должно получить разрешение через OAuth.
Последовательность:

1. Создать приложение и получить Client ID и Client Secret.
2. Настроить OAuth redirect и получить RuName.
3. Отправить продавца на страницу авторизации eBay.
4. Продавец входит в свой аккаунт и разрешает доступ.
5. Приложение получает временный code.
6. Сервер обменивает его на access_token и refresh_token.
7. Когда access token истекает, сервер обновляет его через refresh token.

Для управления товарами и политиками нужны соответствующие разрешения, в частности:

```text
https://api.ebay.com/oauth/api_scope/sell.inventory
https://api.ebay.com/oauth/api_scope/sell.account
```

Адрес выдачи токенов Production:

```http
POST https://api.ebay.com/identity/v1/oauth2/token
```

Для операций продавца нужен пользовательский токен — User access token. Один только Application token, полученный через Client Credentials, не заменяет разрешение продавца.
Токены и Client Secret хранить только на сервере. Для каждого аккаунта продавца — своё подключение и refresh token. Срок действия брать из ответа OAuth, а не задавать предположительно. Официальная инструкция OAuth.

## 4. Что такое SKU, EAN, offer и listing

Это разные сущности:

| Поле / сущность | Значение |
| --- | --- |
| SKU | Уникальный внутренний идентификатор товара у продавца |
| EAN | Реальный товарный штрихкод |
| inventory item | Запись товара: описание, фотографии, характеристики, остаток |
| offer | Условия продажи: категория, цена, политики, площадка |
| offerId | Идентификатор предложения eBay |
| listingId | Идентификатор опубликованного объявления |

Offer здесь не означает ставку покупателя. Это подготовленное продавцом предложение продажи. У одного товара отдельно существуют данные самого товара и условия его размещения. Модель Inventory API.
Практическая рекомендация:

```text
Ваш product_id → seller account → SKU → offerId → listingId
```

Не путать новый внутренний номер с новым EAN: в SKU можно поставить собственный идентификатор, но в EAN нужно передавать настоящий GTIN товара, а не выдумывать штрихкод для создания другого объявления. Требования к товарным идентификаторам зависят от категории. Идентификаторы товаров.

## 5. Что настроить перед первой публикацией

### Политики продавца

Нужны три политики:

- fulfillmentPolicyId — доставка.
- paymentPolicyId — оплата.
- returnPolicyId — возврат.

Продавец должен подключить Business Policies. Политики можно подготовить в аккаунте и использовать их ID в интеграции.

### Местонахождение товара

Нужно создать inventory location и сохранить его ключ:
`merchantLocationKey`
В нём указываются данные местонахождения товара.
Эти настройки должны соответствовать подключённому продавцу и выбранной площадке. Нельзя брать ID политик одного аккаунта и использовать их для другого. Политики и местонахождение входят в подготовку публикации. Последовательность настройки и создания.

## 6. Как получать категории и обязательные атрибуты

Нельзя использовать один универсальный набор характеристик для всех товаров.
Правильная последовательность:

1. Получить дерево категорий для EBAY_DE через getDefaultCategoryTreeId.
2. Найти подходящую конечную категорию через getCategorySuggestions или дерево.
3. Получить её атрибуты через getItemAspectsForCategory.
4. Построить форму по полученным ограничениям.

Пример запроса атрибутов:

```http
GET https://api.ebay.com/commerce/taxonomy/v1/category_tree/{categoryTreeId}/get_item_aspects_for_category?category_id={categoryId}
```

Передавать нужно названия характеристик и значения, соответствующие категории. Учитывать допустимые значения, формат и возможность нескольких значений. Работа с категориями.
Обязательность определяется aspectConstraint.aspectRequired: true. Рекомендуемые характеристики можно заполнять дополнительно, если информация действительно известна. Обязательные характеристики.
Если используется OpenAI, рекомендация такая: передавать ему данные товара вместе со схемой категории, а результат проверять на сервере. Не позволять модели придумывать материал, сертификаты, размеры или совместимость.

## 7. Какие данные передавать

### Данные товара — inventory item

- SKU.
- Название.
- Описание.
- Состояние товара.
- Количество.
- Фотографии.
- Характеристики категории.
- EAN, бренд, MPN — когда применимо.

### Условия продажи — offer

- SKU.
- Площадка.
- Категория.
- Формат продажи.
- Цена и валюта.
- Доступное количество.
- Политики доставки, оплаты и возврата.
- Ключ местонахождения.
- Продолжительность размещения.

Успешно сохранить черновик недостаточно: часть полей становится обязательной именно при публикации. Категория также может требовать дополнительные данные. Обязательные поля публикации.

## 8. Как создать объявление

Базовый адрес:

```text
https://api.ebay.com/sell/inventory/v1
```

Обычно запросы с JSON отправляются с заголовками:

```http
Authorization: Bearer ACCESS_TOKEN
Content-Type: application/json
Content-Language: de-DE
```

### Шаг 1 — создать товар

```http
PUT /inventory_item/{sku}
```

Иллюстративная структура:

```json
{
  "availability": {
    "shipToLocationAvailability": {
      "quantity": 1
    }
  },
  "condition": "NEW",
  "product": {
    "title": "Название товара",
    "description": "Описание товара",
    "imageUrls": [
      "https://your-domain.example/images/product.jpg"
    ],
    "aspects": {
      "ИМЯ_АТРИБУТА_ИЗ_TAXONOMY": [
        "ДОПУСТИМОЕ_ЗНАЧЕНИЕ"
      ]
    }
  }
}
```

Это шаблон структуры, не готовый запрос: URL и атрибуты необходимо заменить. Состояние NEW использовать только для действительно нового товара, когда оно разрешено категорией. Метод создания inventory item.

### Шаг 2 — создать offer

```http
POST /offer
```

Передать условия продажи из предыдущего раздела. Из ответа сохранить:

```json
{
  "offerId": "..."
}
```

### Шаг 3 — опубликовать offer

```http
POST /offer/{offerId}/publish
```

Из успешного ответа сохранить:

```json
{
  "listingId": "..."
}
```

Общая цепочка:

```text
Подготовка аккаунта
→ inventory item
→ offer
→ publish
→ сохранение listingId
```

Создание offer само по себе ещё не публикует объявление. Официальный процесс публикации.

## 9. Как смотреть товары

Основные запросы Inventory API:

| Что получить | Запрос |
| --- | --- |
| Список inventory items | `GET /inventory_item` |
| Товар по SKU | `GET /inventory_item/{sku}` |
| Предложения по SKU | `GET /offer?sku={sku}` |
| Конкретное предложение | `GET /offer/{offerId}` |

Для списков нужно обрабатывать пагинацию. Полный перечень операций есть в справочнике Inventory API.
Для проверки публикации рекомендую:

1. Убедиться, что publish завершился успешно и вернул listingId.
2. Повторно получить offer и проверить его состояние.
3. Проверить объявление в Seller Hub и на странице eBay.

Статус completed собственной очереди не должен означать «товар опубликован». Это разные результаты. В интерфейсе лучше отдельно показывать «обрабатывается», «опубликован», «ошибка» и «снят с продажи».

## 10. Как изменять объявление

| Что изменить | Операция |
| --- | --- |
| Название, характеристики, фотографии | `PUT /inventory_item/{sku}` |
| Цена, политики и другие условия offer | `PUT /offer/{offerId}` |
| Цена и количество пакетно | `POST /bulk_update_price_quantity` |

**Критически важно:** updateOffer — полная замена данных предложения, а не частичный PATCH. Нужно передавать все необходимые сохраняемые поля, включая неизменённые.
Безопасная схема:

```text
GET текущих данных
→ формирование разрешённого request DTO
→ применение изменений
→ PUT
→ повторный GET для проверки
```
Не нужно отправлять ответ GET целиком без разбора: в нём могут находиться поля только для чтения.
Обновление опубликованного offer изменяет действующее объявление; неопубликованный offer после редактирования нужно публиковать отдельно. Редактирование offer.

## 11. Как деактивировать, активировать и удалить

### Снять с продажи с возможностью вернуть

```http
POST /offer/{offerId}/withdraw
```

Объявление завершается, offer сохраняется и становится неопубликованным.

### Вернуть в продажу

Проверить актуальность данных, цену, остаток и политики, затем:

```http
POST /offer/{offerId}/publish
```

После публикации сохранить возвращённый listingId. Не предполагать, что он обязательно останется прежним.

### Удалить offer

```http
DELETE /offer/{offerId}
```

Удаляет предложение и завершает связанное активное объявление. Для обычной кнопки «Деактивировать» лучше использовать withdraw, а не удаление. Семантика операций.

### Удалить inventory item

```http
DELETE /inventory_item/{sku}
```

Это более широкая операция: удаляет inventory item вместе со связанными offer. Её нужно отделять от обычного снятия с продажи и подтверждать пользователю последствия. Управление и удаление объявлений.

## 12. Что делать с уже существующими объявлениями

Не все объявления аккаунта автоматически доступны как Inventory API objects.
Для существующих объявлений, созданных другим способом, предусмотрена миграция:
`bulkMigrateListing`
У неё есть требования к совместимости объявления. Поэтому перед переносом нужно проверить eligibility, а не массово считать все объявления подходящими. Требования миграции.
Если миграция не подходит, нужен отдельный сценарий Trading API. Нельзя просто создать новое объявление вместо найденного старого — это может дать дубликат.

## 13. Проверки, которые нужно сделать до отправки

### Фотографии

- URL доступен извне без авторизации.
- Используется HTTPS.
- Файл действительно является изображением.
- Нет ответа 404 / 410.
- Каждая фотография соответствует требованиям eBay.
- Длинная сторона — минимум 500 пикселей. Требование размеров.

Для большинства категорий поддерживается до 24 фотографий, но есть исключения, включая ограничения для отдельных вариаций. Можно использовать собственный HTTPS-хостинг либо загрузку через eBay Media API. Работа с изображениями.

### Остальные данные

Рекомендую проверять на сервере:

- Категорию и её обязательные атрибуты.
- Допустимые значения и количество значений атрибута.
- Длины конкретных текстовых полей.
- Цену, валюту и остаток.
- Реальный EAN, когда он передаётся.
- Принадлежность политик аккаунту.
- Требования категории к состоянию и дополнительным данным.

Не задавать один общий лимит для всех полей описания: проверять ограничения именно того поля API, которое используется.

## 14. Как организовать интеграцию в его проекте

Это рекомендуемая схема реализации, а не обязательная структура eBay:

```text
Форма товара
    ↓
Серверная валидация
    ↓
Фоновая задача
    ↓
eBay adapter
    ↓
Inventory / Account / Taxonomy API
    ↓
Сохранение результата и ошибок
    ↓
Статус в интерфейсе
```

В базе рекомендую хранить:

```text
local_product_id
seller_account_id
environment
marketplace_id
sku
ean
offer_id
listing_id
publication_status
last_error
last_checked_at
```

Обязательно предусмотреть:

- Обновление OAuth-токенов.
- Таймауты внешних запросов.
- Ограниченные повторы временных ошибок.
- Защиту от двойной публикации.
- Проверку существующего offer после неопределённого результата запроса.
- Журнал операций без секретов.
- Понятные ошибки с названием неправильного поля.
- Раздельные данные Sandbox и Production.

## 15. Порядок внедрения

1. Получить developer keys и подключить продавца через OAuth.
2. Подготовить политики и местонахождение.
3. Подключить категории и атрибуты.
4. Реализовать создание inventory item и offer.
5. Добавить публикацию и проверку результата.
6. Реализовать чтение и редактирование.
7. Добавить снятие, повторную публикацию и отдельное удаление.
8. Пройти полный сценарий в Sandbox.
9. С разрешения владельца выполнить контролируемую проверку в Production.

**Итог:** минимально необходимая цепочка — OAuth → политики и location → категория и атрибуты → inventory item → offer → publish → проверка результата.
Доступы и ограничения аккаунта коллеги я не проверял; реальная публикация может повлечь комиссии eBay. Проект и его настройки не изменял.
